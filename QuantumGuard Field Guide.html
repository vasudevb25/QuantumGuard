QuantumGuard Field Guide

How each part of the system works, why it is there, what its output looks like, and what that output means. Sample outputs come from a copy of your own capture, taken when it held 269 events. Scores were re-measured later on 463 events.

The idea

When attackers break into a Linux machine, the logs are what investigators use to work out what happened. An attacker with root can edit those same logs. Most provenance systems assume their input is honest. QuantumGuard treats the record itself as the thing under attack.

It answers four questions, in this order: Did we record everything? Does the record look tampered with? Can we prove it has not changed? How much evidence survives if it is damaged?

  1. CaptureKernel probe records every program start
  2. NormaliseClean and order raw events
  3. GraphWho ran what, as a graph
  4. DetectRules and a GNN look for tampering
  5. SealHashes and two signatures lock the record
  6. AnchorCopy fingerprints off-site, by risk
  7. SurviveMeasure what evidence is left

How to say this in your review

Detection catches careless attackers and sends the investigator to the right place. It can be beaten by a careful attacker. The seal cannot be beaten this way, because it never asks whether the graph looks wrong, only whether it changed. The two layers do different jobs, and the numbers show that.

GNN figures move by several points each time you train. Adaptive forgery has measured between 7% and 33%, so quote the pattern, not one exact figure.

The old docs claimed "100% detection". That number was real only for the attacks the model trained on. A reviewer who tries a new attack would find this gap in minutes, so it is better that you present it first.

Phase 1: Capture

ebpf/probes.c · ebpf/loader.c · capture/collector.py · capture/cca.py
Purpose
Record every program that starts, in a way that makes lost events provable.
Why eBPF
It runs inside the kernel, so a program cannot avoid it by changing its own behaviour, and it does not depend on any log file an attacker could edit before the data is read.
What it keeps
Anything run by a user with uid 1000 or above, or inside a login session. The login uid is set when someone logs in and survives sudo, so root commands run by a person are recorded, while system services are filtered out as noise.
Why CCA
If event 47 is missing, was it dropped under load or deleted by an attacker? Capture Completeness Attestation records losses as they happen, so anything missing without a record must be deletion.
execve / execveat  program starts
      │
  eBPF probe       in the kernel; keeps login sessions, skips services; counts losses
      │  ring buffer, 16 MB
  loader           C program; prints each event as escaped JSON
      │
  collector        Python; adds Unix time, turns losses into sequence gaps
      ├── raw_events        one row per event, numbered in order
      ├── cca_attestation   one row per gap or restart
      └── completeness_*.json  signed summary, written on exit

Reading it: [87] is the sequence number. code is the name of the program that made the call, here VS Code. The path is the program it tried to start. Several paths in a row means VS Code searching your PATH for docker. That is normal: the probe records the attempt, whether or not the file exists.

The signed certificate lists the range covered and each lost sequence. "complete": true means nothing was lost. false means it names exactly what was lost, which is still a good result, because the loss is on record.

Phase 2: Normalise

graph/service.py: deduplicate, validate, enrich
Purpose
Turn raw events into something consistent, without hiding evidence.
Deduplicate
Two events with the same PID and file within 2 ms count as one. The removed numbers are remembered, so they are not later mistaken for deletion.
Validate
Checks order. After an attested reboot, time is shifted forward so it keeps increasing. Any other backwards jump stays in the graph for Phase 4 to report.
Enrich
Gives each event a process ID, a process_hash of its PID, time and name, and a likely parent.

What the result means on your data: 269 raw events became 247: 22 duplicates were merged, nothing was dropped, and time was shifted once at event 87. Before the fix, only 81 events survived.

Phase 3: Provenance graph

graph/service.py: build
Purpose
Investigators ask "what led to this?". That is a path through a graph, and a flat log cannot answer it directly.
Nodes
Processes, files, and one synthetic session root per user, which adopts processes with no known parent.
Edges
SPAWNS (parent to child process) and EXECUTES (process to file). One event makes one of each, and both carry its sequence and time.
P:ROOT:1000 (session root)
   │ SPAWNS
   ▼
P:100:1  bash ──EXECUTES──▶ F:/usr/bin/python3
   │ SPAWNS
   ▼
P:101:2  python3 ──EXECUTES──▶ F:/usr/bin/git

Reading it: 247 events give about 247 × 2 edges, which matches 494. The 278 nodes are 247 processes plus 30 files plus one root, so your session reran the same 30 programs many times. It writes graphs/provenance_graph.gpickle for later phases and a .graphml copy you can open in other tools.

To see it: python main.py visualize draws one box per program, with runs and tries on each arrow, and writes graphs/provenance_graph.png and .svg. Root programs are red and GNN-flagged programs have an orange border. The full per-process graph stays in the .graphml file.

GraphSAGE model

Rules only catch what someone thought to write down. The GNN learns what tampering tends to look like and gives every node a suspicion score. GraphSAGE fits because a node's score depends on its neighbours, and tampering usually leaves odd patterns around a node as well as in it. It is written by hand in NumPy, and a numerical test checks its gradients.

each node: 38 features  structure, timing, hash validity, uid, name bucket
      │
  layer 1: own features + average of neighbours → 64 values, ReLU
      │
  layer 2: same again, so it sees two hops away → 64 values, ReLU
      │
  output: sigmoid → suspicion score, 0 to 1
      │
  graph alert if 2 or more nodes score above the threshold

Training data: no public dataset of poisoned provenance graphs exists, so the project makes its own: 220 synthetic graphs of up to 300 events, some with normal sudo use, plus your capture, half with attacks applied. Every node an attack touched is labelled 1. Training uses Adam with a heavier loss weight on tampered nodes, since they are rare. The threshold is then raised until fewer than 5% of clean validation graphs alert.

verdict
TAMPERED means a rule found proof. SUSPICIOUS means only the GNN alerted, so confirm with verify. CLEAN means neither did. The brackets say who decided.
confidence
1.0 when a rule fired. The average score of the flagged nodes when only the GNN alerted. 0 when clean.
threshold
How sure the model must be before a node counts. It changes every time you train.

Training metrics: on trained attacks, node F1 was 0.77 with AUC 0.95 in the latest run. At graph level, recall was 1.00, and precision has ranged from 0.88 to 1.00 across runs.

Real captures: the GNN raises false alarms on real data even after retraining on it. A clean 177-event capture came back SUSPICIOUS, although clean synthetic graphs scored 0%. Real use looks unlike the synthetic training data. False alarms also rise with size: 33% of clean 800-event synthetic graphs alerted. Scoring in chunks made it worse, because cutting a graph creates orphan processes. detect now prints a warning in this case. Rules and the seal are not affected by size.

Phase 5: Sealing

crypto/integrity.py
Purpose
Make any later change to the record provable, using mathematics instead of judgement.
Merkle tree
Edges are split into partitions of 128. Each edge, with both its nodes, is hashed, and the hashes are combined to one root. Changing one edge changes the root. You can also prove one edge belongs without revealing the others.
Hash chain
Each partition includes the hash of the one before it, so removing or reordering partitions breaks the chain. Each also records the total count, so removing the newest ones is caught too.
Two signatures
Ed25519 is small and well proven today. ML-DSA-65 (FIPS 204) is designed to resist quantum computers, at 3309 bytes against 64. Both must pass, so an attacker has to break both. This is where the project's name comes from.
Key store
Private keys are encrypted on disk with AES-GCM, using a key derived from your passphrase with scrypt. That is why the wrong passphrase gave you the error you first reported.
Pinning
Each record carries its own public key, so a valid signature alone only proves that somebody signed it. verify now also requires it to be the expected key.
                 root ── signed with Ed25519 AND ML-DSA
                /    \
              h12    h34
             /  \    /  \
           e1   e2  e3   e4      one hash per edge, nodes included

partition 0 ◀── partition 1 ◀── partition 2      each stores the previous hash

Reading it: PASS means the graph is exactly what was sealed. merkle_ok failed means a relation sealed in that partition is missing or changed. unsealed relation(s) are in the graph but were never sealed, which is what insertion looks like. The count of 147 is more than the 48 relations forged here, because adding a run of a file also changes that file's node, and the seal covers every edge attached to it.

Phase 6: Risk-adaptive anchoring

anchoring/risk.py · service.py · ledger.py
Purpose
A signature shows evidence was not edited. It cannot help if root deletes everything. An anchor keeps a copy of the fingerprint somewhere else.
Why by risk
Anchoring costs a blockchain transaction. Anchoring everything is too expensive, and anchoring nothing leaves you exposed. So the most valuable evidence gets the strongest protection.
SignalWeightMeaning
Rule violations0.25Proof of inconsistency in this partition
GNN suspicion0.25How many flagged nodes, and how strongly
Tamper alert0.20Holds the evidence behind a TAMPERED verdict
Privilege activity0.15User changes or root execution
Unattested gap0.10Missing events with no CCA record
Rare program0.05A binary seen very rarely in this capture
TierWhenProtection
Tier 1, immediateScore ≥ 0.45, a tamper alert, or a high/critical rule hitAnchored now. Several in one pass share one transaction
Tier 2, batchedScore ≥ 0.20Held until 8 are waiting, then anchored under one second-level Merkle root
Tier 3, localScore below 0.20Hash chain only, no cost

What the results mean: over 15 synthetic runs, clean captures scored at most 0.018 and tampered ones at least 0.268, so the 0.20 threshold separates them cleanly. Clean runs used 0 ledger transactions. Tampered runs anchored 250 partitions in 16 transactions, which is 15.6 times cheaper than one each. An attack the detector misses still scores like clean data, so it stays Tier 3. It is caught by the seal, but its fingerprints do not get copied off-site early.

The ledger is a local file that imitates a blockchain's behaviour. A real Hyperledger Fabric network is what would stop a root attacker replacing it. FabricLedger refuses to run and does not fake a receipt.

Phase 7: Forensic survivability

evaluation/main.py

Purpose: detection asks "was there an attack?". An investigator's next question is "how much of my evidence can I still use?". This phase damages a copy of the graph in a chosen way and measures what is left.

MeasureQuestion it answersFSI weight
PIS Integrity ScoreOf everything sealed, how much is still present and still matches?0.30
EPR Preservation RatioWhat share of captured events still appear?0.20
GRR Recovery RateWhat share of "A led to B" paths can still be walked?0.25
RA Recovery AccuracyOf what the system calls authentic, how much really is?0.25
FSI Survivability IndexAll four combined into one number

Reading it: 30% of processes were removed and EPR shows about 70% remain, as it should. PIS is 339 ÷ 494. The most useful line is provably deleted: 155, because the investigator can now state exactly how much was removed.

About RA 100%: with sealing this is true by construction, since a matching hash is the original relation. The real measurement is the comparison: under a mixed delete-and-fabricate attack, RA is 80.80% without sealing and 100% with it, because the 72 fabricated relations are rejected. That 19.2 point gain is what sealing is worth.

Reading the columns

The share of attacks where a high or critical rule fired.

The share where the model alone would have alerted.

The verdict the system reports: rules or GNN.

The share where verification failed against a seal made before the attack.

How well scores rank tampered above clean nodes: 1.0 is perfect, 0.5 is guessing. Held-out attacks got 0.42 to 0.76, and six of the seven were at 0.74 or below.

That last point really happened. Before calibration, the GNN appeared to catch about 30% of unseen attacks. It also alarmed on 30% of clean graphs, so it was guessing.

Attacks on the evidence itself

These leave the graph alone and change the sealed records and ledger. All 17 were caught: editing a leaf, root, signed field or either signature; deleting, swapping or truncating partitions; a duplicate leaf; re-signing with an attacker's key; replacing only the ML-DSA key; a fake batch proof; a root that disagrees with the ledger; and editing, rebuilding or removing ledger blocks. The command exits with status 2 if any of these is missed.

Your real capture

The same matrix on 8 windows of your capture gave 0% false alarms and a 100% seal. Treat its GNN numbers as optimistic, because the model trained on this same capture. A new line in the report shows the verdict on the whole capture too, because detect runs on the whole graph and small windows can hide size problems. When I trained on the first half and tested on the second, false alarms on small windows were 0/3 with one seed and 3/3 with another. One capture is too little to claim a real-world false alarm rate, so do not quote one.

Still open

These need a decision or more work, so I left them. They are also in PROJECT_STATUS.md.

  • An exploited root service can go unseen. Login-session capture records sudo, su and root logins. A system service has no login session, so an attacker who gets root by exploiting one looks like every other service and is filtered out. Removing the filter closes this, but records all service activity. This is the biggest remaining capture gap.
  • The GNN is unreliable on real captures. Treat SUSPICIOUS as a prompt to run verify, not as evidence. Training on more realistic data is the fix.
  • Commands typed in a terminal are mostly missing from captures, cause unknown. Captures hold events from VS Code, its scripts and claude, but not python main.py commands run during the capture, including with the original probe. A certificate saying "0 missing" only covers events that reached the collector. Do not claim every exec is captured until this is explained.
  • Parents are guessed from program names. The probe could read the real parent PID from the kernel. Your docs claim "causally correct", which this does not fully support.
  • Only program starts are captured. There are no file reads or network connections.
  • The seal only protects from the moment it is made. Anything altered before seal runs gets sealed as if true. Sealing soon after capture narrows that window.
  • The key store is on the same host. A root attacker can replace it, which is why --trust-file with an off-host copy matters.
  • The ledger is local, and removing its newest blocks is only caught if the anchoring report still exists.
  • GNN generalisation is weak on unseen attacks. Training on the adaptive attacks would raise these numbers, but they would then no longer count as unseen.

Not yet tested

  • Login-session capture compiles, and its field resolves against your kernel's type data, but it has not been loaded into a kernel. That needs root. Run the sudo check below to confirm it. Your own run has already confirmed the earlier probe changes and sealing to PostgreSQL on real systems.
